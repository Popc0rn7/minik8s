Minik8s: A Teaching Kubernetes Core Loop

A lightweight container orchestration system with control plane, node agent, CNI networking, Service proxying, and controller reconciliation.

Goal and Scope

Minik8s does not aim to reproduce all Kubernetes semantics. The goal is to implement a clear, demonstrable core loop from declarative YAML to scheduled Pods, Pod networking, Service access, controller convergence, and state recovery.

  • Kubernetes-like resource workflow: apply, get, describe, delete.
  • Bridge control plane stores state, schedules Pods, and runs controllers.
  • Sailer worker creates Docker containers and manages local data plane.
  • File or etcd-backed Logbook persists objects across control-plane restart.

Bridge combines API, persistence, scheduling, and controllers. Sailer pulls assigned Pods, creates sandboxes, runs CNI, writes status, and syncs Service rules.

Implementation Highlights

Self-built CNI: mooring

Implements CNI ADD/DEL/CHECK, creates bridge/veth, assigns Pod IPs, writes default routes, and cooperates with Sailer for VXLAN/FDB/route synchronization.

Controller reconciliation

Service endpoints, ReplicaSet replicas, HPA scaling, DNS snapshots, Job submitters, and Serverless objects are reconciled by Captain controllers.

Restart recovery

File or etcd-backed state lets bridge recover declared objects after restart while workers continue heartbeating and reconverge status.

Optional Feature: Serverless

The optional feature focuses on a teaching Serverless API model. Function, EventTrigger, and Workflow are first-class Minik8s resources with YAML loaders, Harbor APIs, file/etcd stores, and a minimal execution path.

  • Function: inline Python function object.
  • EventTrigger: connects events to Function references.
  • Workflow: minimal resource model for function chains.

Limits: scale-to-0, reliable ack/retry, dead-letter handling, and complex DAG execution are not complete.

GPU Job Extension

Minik8s supports a minimal Job + Slurm submitter backend. GPU jobs declare accelerator=gpu, submit CUDA source and commands, then collect Slurm .out/.err logs.

Job YAML Submitter Pod SSH / SCP Slurm Queue Logs

This is not a native Kubernetes GPU device plugin; it is a teaching backend for submitting CUDA work to the SJTU Slurm platform.

Known Limits

  • No full Kubernetes watch/resourceVersion/admission/RBAC machinery.
  • CNI, VXLAN, iptables, and NodePort demos require Linux network tools and root.
  • Scheduler is simple and not resource-aware.
  • PV/PVC and Security Context are not implemented.
  • Serverless is an object model and minimal path, not a full platform yet.

Demonstration Path

  1. make build creates minik8s and kubectl.
  2. minik8s init prepares state directories and static manifests.
  3. minik8s bridge starts Harbor, Logbook, scheduler, and controllers.
  4. sailer join/run registers workers and receives PodCIDR.
  5. kubectl apply creates Pods, Services, ReplicaSets, HPA, DNS.
  6. Service endpoints, Pod IPs, Node status, and Logbook recovery are shown by CLI output.
